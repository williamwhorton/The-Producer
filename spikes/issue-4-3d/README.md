# Godot 4: 3D orthographic dollhouse

Disposable presentation proof for [#14](https://github.com/williamwhorton/The-Producer/issues/14).
The fixture in [#4](https://github.com/williamwhorton/The-Producer/issues/4) is
authoritative; the [merged #13 2D prototype](../issue-4-2d/README.md) is the
comparison baseline. This does not select a production engine or rendering mode.

## Launch and walkthrough

From the repository root on Linux/Bazzite, with `godot` on `PATH`:

```sh
godot --path spikes/issue-4-3d
```

The main scene is `res://main.tscn`. No external assets or editor import are needed
to launch it. Tested with **Godot `4.7.2.stable.official.ed1daf0bf`**, Compatibility
renderer, on Bazzite 45 (Kinoite).

1. Ground starts visible in **Cutaway**. Look for olive A, teal B, terracotta C,
   both gold doorway strips and ground markers **1**, **2** and **S**. Click the
   floor of each room to outline it. Click a wall, rim or background to clear.
2. Press **C** to raise the foreground walls and partitions. At the default
   1060×640 framing, a click around `(640,393)` (window pixels from top left)
   selects B in cutaway and clears selection with full walls. Press **C** again
   to lower the obstructing walls to stubs; the two far walls stay up.
3. Press **F** to reveal purple U and its stair symbol. Click the purple floor to
   select U. The slab masks some ground floor detail. **F** again restores the
   ground view and clears the U selection.
4. With the upper floor hidden, press **Space**. Marker 1 jumps to the debug
   start in A, crosses the gold A–B threshold and stops in B. The HUD changes
   from `Running` to `Done`. Space replays the route.
5. **Right-drag** to pan in screen axes and **scroll** to zoom around the center.
   Click a visible floor again to check the selection tracks the camera.

## Exact fixture

One unit corresponds to one abstract cell. Fixture `(x,y)` maps to Godot `(x,z)`;
Godot `y` is elevation. Cell coordinates are zero-based, markers sit at cell
centers, and walls sit on edges, not in walkable cells.

| Element | #4 fixture |
| --- | --- |
| Footprint | 10×10, `(0,0)`–`(9,9)`, exterior walls enclosing the gray rim |
| Ground A, B, C | A `x=1..4, y=1..8`; B `x=5..8, y=1..4`; C `x=5..8, y=5..8` |
| A–B wall / door | Columns 4–5 boundary, rows `1..8`, open at row `3` |
| B–C wall / door | Rows 4–5 boundary, columns `5..8`, open at column `7` |
| Upper U | Same cells as B; stair symbol `(6,3)`; no upper character marker |
| Ground 1, 2, S | `(2,2)`, `(6,2)`, `(7,7)` respectively |
| Debug route for marker 1 | `(3,3)` → `(4,3)` → `(5,3)` through the A–B opening |

## Comparison with #13

| Topic | What this prototype shows |
| --- | --- |
| Camera | Both have fixed-angle pan and centered zoom with the same controls. #13 translates/scales a 2D camera with hand-projected coordinates. Here `Camera3D` provides a similar 2:1 view; pan translates along its right/up axes and zoom changes its orthographic size. Neither prototype tests camera orbit. |
| Occlusion and picking | The 3D depth buffer handles overlaps without #13's projected wall/marker sort. Selection still needs explicit rules: a camera ray tests visible wall boxes and slabs; slab sides and walls block selection; labels, thresholds, stairs and pegs are click-through. #13 uses projected floor and wall polygons instead. |
| Multistory visibility | Both use a fixed cutaway and a ground/ground-plus-upper toggle. In the rendered 3D view some of peg 2 remains visible beneath the upper slab; in #13 the 2D upper layer covered marker 2 in the equivalent default view. Both obscure parts of the ground and benefit from hiding U; 3D alone does not solve room legibility. |
| Navigation | Both replay the same A–B debug route. #13 uses a striped 2D stair glyph; here four stepped blocks are the corresponding symbol. Neither provides actual stair traversal, autonomous navigation or player control of a contestant. |
| Lighting and implementation | In 3D, one key light and ambient fill shade primitive faces; #13 paints face colors directly. 3D could support dynamic lights and shadows, but this exercise doesn't evaluate shadows, atmosphere, cost or performance. Built-in projection/depth replace 2D drawing/sort logic; mesh setup, materials, camera-space input and ray picking take its place. |
| Editor workflow | The 3D scene exposes the camera, light, environment and floor roots in the Inspector, but the house meshes are built at runtime from the fixture. Inspect the running scene for layout, or edit the fixture in GDScript; this is not an editor-authored modular house. #13's house is also generated by script, using `_draw()`. |

The prototype does not model collision, pathfinding, private contestant state,
supernatural behavior, or any production systems. No C#, external service,
sockets, database, paid cloud call, imported runtime artwork or plug-ins are used.
Cutaway is fixed to the viewing side; zooming or dragging can move the house under
the HUD. This comparison is not an engine recommendation.

## Evidence

Executed from the repository root:

```sh
godot --headless --path spikes/issue-4-3d --editor --import
godot --headless --path spikes/issue-4-3d --quit-after 2
godot --headless --path spikes/issue-4-3d --script res://tests/check_fixture.gd
```

The import and main scene exited 0 with no script errors on the final run.
The test exited 0 with
`PASS: #4 3D fixture, wall and floor occlusion, room picking, and scripted A–B route`.
It checks all ground room cells, ground/upper slabs, both perimeters and
partitions with exact wall gaps, threshold/marker/stair placement, pick blocking,
selection clearing and the route through the doorway.
The unchanged #13 baseline also passed
`godot --headless --path spikes/issue-4-2d --script res://tests/check_fixture.gd`.

Both projects were rendered under Xvfb on Bazzite. The launch commands below
reproduce the display and renderer settings used (the evidence session started
each Godot process inside `xvfb-run`, sent input with `xdotool` and captured the
1060×640 window with `import -window`):

```sh
xvfb-run -a -s '-screen 0 1280x800x24' env LIBGL_ALWAYS_SOFTWARE=1 \
  godot --path spikes/issue-4-3d --display-driver x11
xvfb-run -a -s '-screen 0 1280x800x24' env LIBGL_ALWAYS_SOFTWARE=1 \
  godot --path spikes/issue-4-2d --display-driver x11
```

Inspected 3D captures showed [ground and all markers](evidence/ground.png), A/B/C
selection, [B picked in cutaway](evidence/selected-b.png) and [the same click
blocked by a full wall](evidence/full-walls.png), [U selected and the stair
visible](evidence/upper.png), U hidden with its selection cleared, the marker
[crossing the opening](evidence/route-mid.png) and [stopping in B](evidence/route-end.png),
and [C picked after pan and zoom](evidence/camera.png). Zooming back out retained
the pan offset. For #13, the full-wall and upper-floor views were inspected in the
same display setup. Both GUI logs reported Mesa llvmpipe and the expected virtual
display V-Sync warning, with no script/runtime errors observed. Native
compositor/GPU behavior was not verified in this run.

Opening `res://main.tscn` with
`godot --editor --path spikes/issue-4-3d --display-driver x11 res://main.tscn`
in the virtual display showed the camera gizmo and editor grid, but no house
meshes until running the project, as expected for the scripted fixture.
